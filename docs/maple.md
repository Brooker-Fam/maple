# Maple's Log (`/maple`)

A private, collaborative newborn tracker for Maple Jane: nursing (left/right timers), bottles, pumping, diapers with stool colors, sleep, tummy time, baths, temperature, vitals and skin checks, growth with WHO percentiles, notes and questions for the doctor, photos and milestones. Matt and Brittany (and anyone they invite) log from their phones, from Claude or ChatGPT (MCP), or hands-free with Siri. A separate area "for mom" keeps her food and drinks, medicines, temperature, questions for her OB and check-ins, with warning signs and help lines (see [For mom](#for-mom)).

It's a family side project. The public site at `/` (home, terms, privacy and a waitlist; see CLAUDE.md, "The public site") links to it as "Family sign-in"; the app itself is `noindex`.

## Setup checklist (production)

1. **Google sign-in.** Maple uses `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET` (the same OAuth client brooker-wedding uses). Google only redirects to registered URIs, so `https://maplebaby.app/api/maple/auth/callback`, `https://brooker.family/api/maple/auth/callback` (phones that installed Maple at the old address sign in through its forwarding, and Google must send them back to the host they started on, where the state cookie is) and `http://localhost:3000/api/maple/auth/callback` (local dev) must be authorized redirect URIs on that client: Google Cloud Console → APIs & Services → Credentials → the OAuth 2.0 client → Authorized redirect URIs. The admin username/password also works on the sign-in screen (you'll appear as "Admin"; rename yourself in Settings → People & permissions).
2. **Other sign-in methods and who can join.** Email codes use Resend; Sign in with Apple needs its own Apple Developer configuration. See [Sign-in setup](auth.md) for the exact variables, callback and verification steps. Each option appears only when configured. `/signup` creates a separate family when effective sign-up is open. An existing member signs into their own family. Owners can invite by email or with a one-time link from Settings → People & permissions. `MAPLE_ALLOWED_EMAILS` applies to legacy family 1 access.
3. **Private photo storage (required for uploads).** Vercel → Storage → create a Blob store with **Private** access (e.g. `maple-private`). Copy its read-write token into a new env var `MAPLE_BLOB_READ_WRITE_TOKEN`. Don't connect it with the default `BLOB_*` names, or it will shadow the guest-photo store.
   Without it, new uploads are refused. Existing Maple photos have been migrated to private storage. Retain `BLOB_READ_WRITE_TOKEN` for legacy compatibility and orphan cleanup; photos are served through the signed-in proxy (`/api/maple/photo`).
4. **`MCP_SECRET`.** Set it to a long random string. Otherwise MCP tokens are derived from `ADMIN_PASS`, and changing the admin password would disconnect Claude and ChatGPT.
5. **The contact inbox.** `/privacy` and `/terms` name `hello@maplebaby.app` (`CONTACT_EMAIL` in `src/components/site/legal.tsx`) as the way to have a log deleted or leave the waitlist. The domain's DNS is Vercel's, and it needs MX records for a mailbox or a forwarding service (Vercel → Domains → maplebaby.app → DNS records) before that address receives anything. Send a test message and see it arrive.
6. **AI Gateway credit for the chat.** The chat runs on the team's AI Gateway Credits through the project's OIDC token. On the free tier the chat's model is refused (403 "Free tier users do not have access to this model"). Top up: Vercel dashboard → AI Gateway (sidebar) → the credit balance button (upper right) → choose an amount → Continue to Payment → Confirm and Pay. The same dialog has auto top-up (Change, then a threshold and amount). Per-request zero data retention, which every chat request asks for, is listed for Pro and Enterprise teams only. A team or project budget (`vercel ai-gateway budgets set …`) is a hard cap above the app's own `MAPLE_CHAT_*_BUDGET_MICRO` limits.

Migrations run on build (`maple_babies` is seeded with Maple Jane, due 2026-10-20).

## Connecting Claude and ChatGPT

Full instructions with copy buttons are at `/maple/connect`. The MCP server URL is `https://maplebaby.app/api/maple/mcp` (Streamable HTTP; there is no SSE).

- **Claude** (web, desktop, mobile): Settings → Connectors → Add custom connector → paste the URL → Connect → Continue with Google.
- **ChatGPT** (web, developer mode / custom connectors): add a custom MCP server with the same URL and OAuth.
- **Claude Code:** `claude mcp add --transport http maple https://maplebaby.app/api/maple/mcp`.
- **brooker-wedding's "Brooker Family Calendar" connector** (`brooker.family/api/mcp`, admin login) still carries Maple's tools next to `calendar_exec`, from its own copy of this code, until Maple is removed from brooker-wedding. Its entries are credited to "Admin" unless an owner signed in with Google turns on Settings → Shortcuts & assistants → "Calendar connector logs as me" (`settings.admin_as`, which can only be set to yourself). If an owner turns off the admin login for Maple, those tools refuse.

OAuth reuses the site's `/oauth/*` shim. A Maple connection (detected by the RFC 8707 `resource` parameter, or the `maple` scope) signs in with the same Google session as the app, and the token is minted for `maple:<email>`, so entries show "via Claude / via ChatGPT" under the right person.

- **Bound to this server.** Tokens are bound to exactly `https://maplebaby.app/api/maple/mcp`. Any other resource is refused at consent, so another MCP server can't obtain or replay a parent's token.
- **One server per token.** A Maple token names this server's URL, so brooker-wedding's calendar and RSVP servers refuse it, and Maple refuses theirs.
- **Refresh tokens, for Claude, ChatGPT and local apps only.** A code sent anywhere else (say, a phishing page) gets a 30-day token and no renewal. Each refresh hands out a new refresh token, so connectors in use don't expire. They're stateless, so an old one stays valid until it expires. Admin-login ones last 90 days (the admin login can run code on the calendar and RSVP servers) and die when `ADMIN_PASS` or `MCP_SECRET` changes. Family members' last a year and are re-checked against membership.

## Access and revocation

- **Sign-in methods:** Google, a one-time email code, and Apple all resolve to the existing member key before family access is checked. `maple_auth_identities` connects verified addresses and Apple subjects to that key; it grants no membership by itself. Family settings can connect another email or Apple account while signed in. Independent accounts/logs are never merged automatically; use the original method first, then connect the new method. Setup, limits and account deletion details: [auth.md](auth.md).
- **Removing someone** (Settings → People & permissions) ends everything at once: their sessions, MCP connections (checked on every request and every refresh) and Siri tokens. Removal leaves a tombstone, so an address on `MAPLE_ALLOWED_EMAILS` can't simply sign back in. Inviting them again lifts it.
- **The admin password login** shows up in Settings → People & permissions as "Admin". A Google owner can remove it, which turns off the admin password and admin MCP access for Maple only. Delete the `admin` row from `maple_removed` to turn it back on.
- **Changing `ADMIN_PASS`** signs Admin out of Maple, and revokes admin MCP tokens issued since this change.
- **The session cookie** is scoped to `/api/maple` and `/oauth/authorize`, so the `/ingest` analytics proxy never sees it.

## Hands-free (Siri / Shortcuts)

Settings → Shortcuts & assistants → Hands-free with Siri creates a personal token. An iOS Shortcut does *Get Contents of URL* (`POST https://maplebaby.app/api/maple/quick`, header `Authorization: Bearer maple_…`, JSON `{"action":"pee"}`), then *Speak Text* with the response's `speak` field.

Actions: `pee`, `poop`, `both`, `nurse_left`, `nurse_right`, `switch`, `back_and_forth`, `stop`, `sleep`, `wake`, `vitamin_d`, `bottle` (with `amount_oz`), `status`, and mom's `mom_status` and `mom_dose` (see [For mom](#for-mom)).

Going back and forth: `back_and_forth` with a feed running stops tracking sides from now ("Going back and forth from 9:14, so there's nothing to switch."; a side under a minute old turns both instead, and a paused feed goes back on going both). With nothing running it says "Start the feed on a side first.", since the next side alternates from the side she started on. While she's going both (or on a break from it), `switch` says "She's going back and forth, so there's nothing to switch." instead of guessing a side, and `nurse_left` / `nurse_right` track sides again ("Tracking sides again: she's on the left."). A forgotten feed is refused the same way as `nurse_*`. There's no Siri pause: a stop and a new feed within 10 minutes count as one feed anyway. `status` speaks feeds as Today counts them: "Maple last ate 45 minutes ago, starting on the left, so start on the right next." (with ", or whichever side feels fuller" after back and forth), and after a cluster "Maple cluster fed from 6:02 to 8:40 PM: 4 feeds, 1 hour 52 minutes of nursing. She last ate 45 minutes ago, …"; after a long back-and-forth feed it says when she finished and what last fed counts from ("Maple finished a long feed 5 minutes ago, starting on the right and going back and forth. Last fed counts from 40 minutes before she finished: 45 minutes ago. Start on the left next, or whichever side feels fuller."); nursing now, it says when she's going back and forth, when a break began ("Maple is nursing now, on a break since 2:25 AM, 40 minutes in.", never the last side tracked) and which feed of a cluster this is (`lastFedSpeak` in `mcp-tools.ts`, shared with `maple_status`'s `speak`).

`nurse_left` / `nurse_right` during a running feed switch to (or resume on) that side, unless the feed looks forgotten (`staleFeed` in `feed.ts`, the same rule as MCP `start_timer`): nothing tapped on it for an hour, or (with a start time given, on a break) a time over 30 minutes after she came off. It's judged by the newest stretch start/end or tap, not the feed start, so a long cluster feed tapped a minute ago still resumes, and so does one she dozed off for half an hour. A stale one is refused out loud ("Stop that one first, then start the new feed").

## Opening family sign-up

`/signup` is the public entry point. With `MAPLE_SIGNUP=open`, it offers the configured Google, email and Apple methods, then `/maple` runs onboarding. All methods use the same invite checks, terms, family limits and membership rules. Effective sign-up remains closed while family columns have defaults or missing constraints, signing keys are shared, or recent unassigned legacy notification claims remain.

The separate contract command is `pnpm exec tsx scripts/family-contract.ts --expected-host <unpooled-host> --expected-database <database> --apply`, with `DATABASE_URL_UNPOOLED` supplied through the environment. It locks the Maple tables, removes family defaults, replaces global keys with family keys, validates foreign keys, and checks that rows are unchanged, all in one transaction. A rerun is safe. `--rollback` restores the expanded schema only while every family-owned row still belongs to family 1. Keep sign-up off before reversal. Once other families exist, use a forward repair.

Deploy the compatible `migrate.ts` before applying the contract. Builds detect the family primary key and retain it; they must not restore global uniqueness after the contract. The minimum compatible commit is [`b2155bb`](https://github.com/Brooker-Fam/maple/commit/b2155bb699b32241a1d6c5d81ed43c7299578c2e). Deployments from before it are not rollback targets after sign-up opens.

The Maple-only session and MCP keys retain their previous keys for family 1 compatibility. Preserve the pinned VAPID pair when rotating either key. New and migrated photos use the private Maple Blob token; the legacy public token is retained for compatibility and orphan cleanup.

## In-app chat

**Chat** is a tab like Today or Moments, there in every state (before the birth, while a timer runs, for view-only guests). Each person has one continuous conversation, their own: no New chat, no list of chats, and nobody else's shows (her medicines can be in hers). The page fills what the phone can see (`visualViewport`, so the iPhone keyboard never covers the composer): a Chat header like the other tabs', messages that scroll (theirs right, Maple's left), and the composer on the tab bar, or on the keyboard while it's up. It opens on the newest message the first time, preserves a reading position across tab switches, and offers "Latest reply" when new content is below. "Show earlier" loads older ones a page at a time, and "Delete chat history" removes all of it for good. It loads on first visit and then stays mounted behind the other tabs, so a draft and a reply still coming survive a tab switch. The composer stays available while a reply runs or the phone is offline: up to ten messages can wait in a visible queue. Drafts and queued text persist in this browser, scoped to family and member; sign-out or deleting chat history clears them. Reload pauses waiting messages until Resume is tapped. An uncertain send is checked against its server receipt before any retry, edit or discard. It runs Maple's own MCP tools as the signed-in person, so what it logs reads "(logged by Matt via Maple chat)" in results, "via Maple chat" on rows, and "From Maple chat." in her Logged notices. The tab sends the phone's `X-Maple-Device` id and the chat's tools pass it to her dose writes, so that notice skips the phone the chat ran on, as it does for a tap in the app. The same device id binds a phone-preference card to the phone where it was requested. Code: `src/lib/maple/chat/` (adapter, prompt, prices, caps, storage, crisis check, the POST in `post.ts`, the turn) and `src/app/api/maple/chat/route.ts`; the tab is `src/components/maple/chat/` (`ChatTab.tsx`, `useChatThread.ts`; loaded on first visit, so Today's bundle doesn't carry the AI SDK).

- **Model:** `zai/glm-5.3-flash` through Vercel AI Gateway, authenticated by the deployment's OIDC token (no API key), with low reasoning (the Gateway maps the AI SDK's top-level `reasoning: "low"` to GLM's effort; the listing offers low, high and max). `MAPLE_CHAT_MODEL` overrides it, but only to a model with a row in `chat/prices.ts` (`anthropic/claude-haiku-5.5`, `anthropic/claude-sonnet-5.5`, `openai/gpt-6-luna` and `alibaba/qwen3.8-flash` have one, each with only its ZDR providers at or under its row): an unpriced model turns the chat off rather than run uncounted. Every request carries `zeroDataRetention: true` and `disallowPromptTraining: true` (`GATEWAY_PRIVACY` in `chat/caps.ts`) and `only`, the price row's `providers`; a check confirms the model request has all three, low reasoning and 1,500 output tokens. Vercel documents that the Gateway then routes only to providers that keep nothing and train on nothing, and fails rather than fall back when none is available; for GLM-5.3-Flash only some of its providers qualify (the listing says `zdr: "some"`). Neither that fail-closed behavior nor `disallowPromptTraining` taking effect has been tested here; one synthetic smoke run (four steps) was served by baseten, which is on the list. GLM's price row is the Gateway's listed price (input $0.15, cache read $0.03, output $0.50 per million tokens, no cache-write price, so writes count as input). Its price varies by provider, and some ZDR providers charge far more (morph's cache reads 25×, modal 3×, wafer's cache reads 1.8×), so `providers` names only the ZDR ones at or under the row (`/v1/models/zai/glm-5.3-flash/endpoints`, checked 2026-10-26), without deepinfra, which at 10 tokens a second can't finish a reply inside a step's 25 seconds. A provider's price can change: recheck that listing before trusting the budgets, and when a model's row changes. Anthropic's cache breakpoints go only on `anthropic/*` models (`usesCacheBreakpoints` in `chat/prompt.ts`); GLM's providers cache the repeated prefix on their own. If the Gateway refuses the model (a 401 or 403, such as the free tier's "Free tier users do not have access to this model"), the chat says it isn't available and logging carries on. Buying Gateway credits moves the whole guava-tri team to the paid tier.
- **Terms first** (`maple_consents`, `src/lib/maple/consent.ts`): before a member's first message the tab shows a short card (Maple is a tracker, not medical advice; 911, 988 and the maternal hotline; what they type and the parts of the log the chat reads go to an AI model through AI Gateway with zero data retention requested; Terms and Privacy) with Accept, which stores their `chat` consent on the server. The POST refuses a message, or an approval tap, without it (403, `code: "terms"`, before anything is counted or locked; the crisis card still shows), and the card comes back. A consent counts only at its kind's current version (`CONSENT_VERSION`): raise it to ask everyone again.
- **Her page** (her food and drinks, medicines and doses, temperatures and questions for her OB) reaches the chat only after she has turned that on herself (consent kind `chat_care`, version 2, under her own member id: `maple_care_people.member`, the same match as `careAccess`'s `self`, never the admin login; a consent from before her page was made, as after "delete everything" on it, doesn't count). Her own terms card has the switch "Let the chat see my food, drinks, medicines, temperatures and OB questions" (off to start), and she can change it in Settings → Chat privacy or her page's Settings; everyone else reads "Brittany's food, drinks, medicines, temperatures and OB questions aren't available to the chat." Version 1 consent does not open her page; she must accept the expanded scope herself. Until then, on the server: her tools aren't in the chat's tool set, every chat tool call carries `care: false` so Maple's tools leave her out (`ctx.care` in `mcp-tools.ts`: `maple_status`'s and `daily_summary`'s lines for her, `log_medicine`'s note that she has the same medicine, and `undo_last` taking back her entries all read her page as absent; a chat call without the flag counts as closed), and the prompt says the chat can't see her page and has it ask "Maple's or Brittany's?" before logging any medicine but vitamin D (her list, which the open chat checks, is out of sight). A thread that ever ran with her page open (`care_open`; older threads all count) never goes back to the model while it's closed: its history can quote her results and the replies that repeat them, so the POST answers `code: "new_chat"` and the phone sends the message again in a new thread, which the tab shows under the old one after a hairline, as one conversation. Only that new thread goes to the model. While her page's row is the plain name "Brittany" (no member's email), nobody can turn it on, so it stays closed.
- **Tools** (`chat/tools.ts`): the MCP registrations, recorded once with a stand-in server and run unchanged with `via: "chat"`. Members get all of them except `set_mom_medicine` and `add_mom_medicines` (her list changes only in the app, where adding one is a real tap), `record_birth` once she's born, and the rest of her tools until she turns on `chat_care` (below); view-only guests get Maple's five reads (`maple_status`, `list_entries`, `daily_summary`, `get_moments`, `list_doctor_questions`), decided on the server, and the write handlers refuse them anyway. `show_help` puts the help card under the reply. `delete_entry`, and `fix_mom_entry` with `action: "delete"`, wait for a tap on a Delete / Keep card; the phone can only send `approved` and `reason` for the server's own pending request. Nothing else waits: `undo_last` (which takes back her food, drinks and doses too), `restore_entry`, `update_entry` (Maple's medicine name, dose or time) and `fix_mom_entry` with `action: "update"` (a dose's time, or skipped) run on the model's word, and a change to a dose moves her next "OK after" time and its reminders. A message sent instead of tapping counts as Keep. A tool result over 20,000 characters is cut before the model reads it.
- **Settings and navigation:** `get_settings` reads an allowlist of family display preferences, baby name/nickname and pediatrician contacts. `propose_setting` shows an Apply card; `/api/maple/chat/settings` resolves the stored proposal, rechecks membership/consent, compares the previous value and atomically updates the setting plus its chat receipt. Undo uses the same conflict checks. Family proposals are bound to the original active baby; phone units, theme and night look run through the existing local providers and report their outcome back, bound to the device. Viewers can change their own phone preferences, never shared settings. `open_screen` offers buttons to exact app sections or existing sheets, including notification setup, photos, doctor questions and medicine plans. It never grants notification permission, changes access or schedules arbitrary reminders.
- **Search and current cards:** `search_entries` reads literal text, kind, local-day or exact-time filters, and doctor questions over at most 366 days. Pages contain at most 20 rows, with a sealed cursor and fresh family/member/current-baby checks on every page. Results open current entries for Edit and allow doctor questions to be marked asked or reopened using the existing version guard. Saved baby and care cards read `/api/maple/chat/entry` while visible to reconcile edits and soft deletions; care also requires current chat-care consent. An unavailable status is labeled historical, with no speculative Edit/Undo controls. Internal references stay out of display text.
- **Delivery receipts:** acceptance stores a private delivery receipt, canonical user message and daily count atomically before model work. Same-ID retries never run a second model turn or write; changing the payload under that ID is refused. Cancellation races atomically with acceptance, so a later-arriving cancelled request cannot execute. Receipts contain IDs, times and an HMAC fingerprint, no message text, and survive chat-history deletion; up to 200 receipts older than eight days are cleared for the current member when chat is used. A message older than seven days cannot newly execute. Cancellation has its own 50-per-UTC-day allowance. New tables and the cancellation counter are additive; older deployments ignore them.
- **Undo across channels:** `"chat"` counts as an assistant source, so "undo that" in the chat can take back something the same person logged through Claude in the last 30 minutes, and Claude's `undo_last` can take back a chat entry. That's intended.
- **What shows:** the reply as plain text, with any em or en dash the model writes rewritten on the server as it streams (a comma, "to" between numbers, "- " at a line's start; `chat/dashes.ts`), so the saved reply matches; internal entry and timer IDs are hidden when replies and tool receipts render (`chat/display.ts`), including earlier messages and streaming replies, while the raw tool IDs remain available for edits and Undo; a receipt per entry the reply saved, with Undo (`remove`, which has its own undo toast); "Not saved yet" for a likely duplicate; Restore after a delete; every health alert in a result as its card, word for word, with the call button (her OB for hers). The model is also told to say them.
- **Activity and recovery:** the tab owns one status row for the active turn, including hidden reasoning and gaps between tools. Labels reflect the actual operation, and a pending question says it is waiting for an answer. Initial history loading, failed history reads and recovery of a turn still running on the server have separate states. Recovery never resends a write. Drafts remain editable; additional sends enter the queue. The queue pauses for a clarification, deletion approval, failed reply or disconnection. Card-generated prompts preserve the draft. Delivery IDs and original submission times stay fixed across retries; write tools interpret relative times against that submission, while read tools and the context snapshot use the current log. Failed sends retain their text. Edit/Discard of an attempted message first records a server cancellation; if acceptance already won, the app reads the outcome instead of claiming it cancelled a write.
- **Ask from the app:** Today, History, Patterns and Moments offer questions about the displayed dates and filters. Saved baby-entry sheets offer “Ask about this entry,” identifying the saved entry and its local time. These buttons open Chat with an editable question and never send it. An existing draft stays intact, with an explicit Add to draft or Dismiss question choice. Entry sheets honor unsaved-edit guards before closing; entries waiting to sync have no chat action. Chat consent and viewer permissions still apply. Pending questions belong to the current family, member and baby.
- **Questions:** the in-app-only `ask_user` tool displays a question with a few choices and a typed-answer option, then ends its request. The next tap resumes the same assistant turn. The server matches the stored question and call, accepts only a valid choice or bounded text, constructs its own answer result, and ignores any client-supplied history or log output. An ordinary composer message supersedes pending questions; delete approvals remain separate. Answered/older cards are read-only. The assistant asks only for needed information it cannot find in the log.
- **Charts:** the in-app-only, read-only `show_chart` tool supplies versioned, bounded snapshots (`chat/charts.ts`, `chat/chart-tools.ts`). Activity covers 14 local days, with 7/14-day and feeds/logged sleep/wet-and-dirty diaper controls; missing logs are distinct from recorded values and today is marked partial. Growth uses numeric recorded weights plus birth weight and the same WHO reading calculations as History, capped at 60 recorded weights. The model chooses a chart type and range, never chart values. Cards show their date range and as-of time; refreshing starts a new authorized read, preserving the earlier snapshot. Chart data is kept with the conversation and removed with chat history. The model receives a compact tool summary rather than the full chart payload.
- **Saved-entry actions:** receipts offer Edit through the existing entry editor and Undo; restoration uses the existing restore action. Buttons show pending state and only report success after the operation confirms it. A failed action keeps its retry available. The prompt avoids repeating the receipt in a second confirmation, while retaining extra context and health alerts.
- **Crisis:** before anything else, the server checks the message for words about harming oneself or someone else (`chat/crisis.ts`): first person or a report about someone else ("my wife said she wants to hurt herself"), passive phrasings ("I don't want to be here") and overdoses, with harm to others only when a person is its subject. It leans toward a match, keeping ordinary baby talk ("she took the whole bottle") out. A match always adds the help card (911, Call/Text 988, the National Maternal Mental Health Hotline) above the reply, whatever the model says; the prompt has it open with `CRISIS_REPLY`. A message turned away before the model runs (a limit, a busy thread, the chat off, the log down, too long) answers with `help: "crisis"` and the sheet shows the card under the problem; the phone runs the same check, so offline it shows the card too. A reply the model declines (a content filter), even partway through, gets `CHAT_REFUSAL` and the same lines, plus her pediatrician's numbers.
- **Prompt:** `MAPLE_INSTRUCTIONS` plus `CHAT_ADDENDUM` (or the viewer's, or `CHAT_ADDENDUM_CARE_CLOSED` while her page is closed to the chat), cached with the tools as one prefix. Each user message is stored opening with `[App]` lines: `Now:` (time, her age, who's signed in), then the log as it stood (`logState` in `mcp-tools.ts`, maple_status's own lines: any running timer with its side now, since when, paused or back and forth and its total, her last feed, the next side, the last diapers and sleep, today's counts, and her next medicine only when her page is open to the chat and the person isn't a viewer). The lines are read once when the message arrives and stored with it (`data-context`'s `line` and `state`), never recomputed, so history replays byte for byte and stays cached; a message stored before `state` existed reads as it did. A failed read leaves the log's lines out (the tools still work); the log being down turns the message away uncounted. The prompt says the person's words follow those lines (a typed `[App]` line is theirs), to answer from them and the tools before asking anything, to stop a running timer at the time said when the person says it ended (never asking how long or which side), to start one when they say it's going on now (never for past tense like "she ate"), to log what happened right away with the time they said and only the details they gave (never what was in a bottle unless they said, which the tool's `milk` field says too), never to promise something for later (it acts only when a message comes in, so "tell me when she wakes and I'll stop it"), to rely on the saved-entry confirmation and add only useful context without internal entry or timer IDs (the shared MCP entry-number instruction is disabled for in-app chat), and to write plain text without markdown or dashes. On Anthropic models a second cache breakpoint moves to the newest message each step.
- **Storage** (`maple_chat_threads`, `maple_chat_messages`, `maple_ai_usage`): a thread is one member's only, and their threads read as one conversation: GET (`chat/history.ts`) returns this member's newest messages across them, in the family they're signed in to, a page at a time (`before`), and which thread new messages go to (their newest); DELETE removes all of them (that family's) for good. Threads stay the server's unit only so a thread that ran with her page open can be left behind. A viewer opens only threads that ran as a viewer throughout (`viewer_only`), so someone made a viewer can't reread her medicines from older chats. Messages are stored without trimming. Approval and question continuations carry on the same assistant reply; question answers are validated and stored before continuing. A new composer message marks pending approvals as Keep and pending questions as superseded. One turn at a time per family/member, including two phones starting different threads (`maple_chat_member_locks`, 70-second leases), as well as the existing per-thread lock; the reply is saved when it finishes, even if the phone locked halfway. When an answer stops early on the phone (a dropped connection, or a refusal), the tab shows a fixed line, never the browser's error, then reloads the chat from the server once its turn is over (GET says whether the current thread is `busy`), so the full reply and its receipts appear; a turned-away Delete tap shows its card again. Usage rows are token counts and integer micro-dollar cost per step, no content, and they outlive their thread, as does `maple_chat_daily` (messages per member per family day), so deleting a chat doesn't reset the day's count. Nothing about a message goes to logs or PostHog: every error in a POST, before the stream or in it, is logged and reported as its class and status only (`scrub` in `chat/post.ts`), and Maple's MCP tool errors as their code. Message text is stored without NUL, other control characters or lone surrogates, which Postgres's jsonb refuses with an error that quotes the text.
- **Limits** (fail closed, a 429 that says "That's the chat's limit for today. Logging works as usual."): 6 model steps per message, question and approval continuations included (an approval may get one final step to report its result; a question cannot add a step past the cap); 1,500 output tokens and low reasoning per step; 2,000 characters a message; 60 messages a day per owner or member, 20 per viewer; a family budget of `MAPLE_CHAT_DAILY_BUDGET_MICRO` (default 500000, $0.50) a day and `MAPLE_CHAT_MONTHLY_BUDGET_MICRO` (default 5000000, $5) a month for the Brookers, in micro-dollars (a value that isn't a whole number counts as 0); every other family gets $0.50 a day and $5 a month (`FAMILY_DAILY_BUDGET_DEFAULT` / `FAMILY_MONTHLY_BUDGET_DEFAULT` in `chat/caps.ts`) unless its own `maple_families.ai_daily_micro` / `ai_monthly_micro` say otherwise (`familyBudgets`). The conversation never ends, so the model reads only its recent end (`modelWindow` in `chat/window.ts`): whole exchanges, newest first, at most 24 messages and 12K tokens by the turn's own estimate (characters / 3, using compact tool text rather than UI-only snapshots), the newest exchange always; a turn loads at most the thread's last 60 messages. With the cached prefix (instructions and tools) that keeps a first step well under the step limit with room for a whole tool result, and a check holds it there. A turn ends after a step whose prompt passes 60K (the reply says so; the tools stay on, so the cached prefix holds). That keeps each request's cost bounded (and, on Haiku, under its 5× price above 100K, which its price row counts if a step passes it). A step that never reports its usage (it timed out or failed partway) counts at an estimate: its whole prompt as a cache write plus 1,500 output tokens; a request the Gateway turns away (a 4xx) counts nothing. Caps are checked before the thread is locked, so requests running at once can each pass the same check. Haiku's row assumes no US-only inference (that would add 10%); requests don't ask for a region. The Gateway's own budget for the project is the backstop; set it in the dashboard (CLI 54.20.0 has no budgets command). Every family but the Brookers also shares one monthly ceiling, `MAPLE_CHAT_GLOBAL_MONTHLY_MICRO` (default 25000000, $25, counted per UTC month), read before every turn of the chat and of the onboarding chat; past it, or with `maple_families.settings.chat_paused` set for a family, its chats answer the month's limit message.

## How it works

- **Data** lives in `maple_entries`: one row per event, with `kind` plus JSONB `data` in metric units (g, cm, °C, ml). The UI shows lb/oz, in, °F and fl oz by default.
  - Running timers are rows with `active = TRUE`. A unique index allows one running timer per kind.
  - `client_id` makes retries idempotent.
  - Deletes are soft deletes, so they can be undone.
- **Shared logic** in `src/lib/maple/` is pure TypeScript, used by the browser, the REST routes and the MCP tools alike:
  - `types.ts` holds the shapes.
  - `time.ts` holds time-zone and DST-safe helpers, plus `parseWhen` for times like "3:10am", "20 min ago" and "yesterday 11pm".
  - `feed.ts` is the nursing engine, shared by the server, the app's optimistic updates and previews, and the MCP tools (checked by `npm run check:maple-feed`). A feed is a list of stretches (`{side, start, end}`); the gaps between them are breaks. `feedParts` turns that into what the card and sheets list (Left, Break, Right…), and every fix moves exactly one **moment**: the feed start, a switch, when she came off, when she went back on, or the end (`moveEdge`, with `edgeBounds` for the limits). `setSide` fixes which side a part was, `undoLastTap` takes back a mistaken switch/pause/resume, and `addPart` adds a side to a finished feed. Nothing moves a neighbouring side as a side effect, and a fix never eats past a break.
  - A Switch tapped within 15 s of a tapped resume (one that made its own part) changes the side she went back on instead of adding a second-long part (`resided`; the break stays, and undo still goes back to paused): "Back on the Left, not the Right". A resume given an earlier time is a real part, so a Switch after it is a switch. Switching back within 15 s of a switch still undoes that switch (`reverted`).
  - Words: after a break it's "back on the Right" only when she came off the Right; otherwise "On the Right" / "When did she go on the Right?" (`momentQuestion(moment, side, prev)`).
  - **Back and forth.** A stretch's side is `"L"`, `"R"` or `"B"`: both sides, not tracked (`StretchSide`; `Side` stays L/R for `first_side`, `last_side`, the next side and anything a person picks). `switchTo(data, "B")` ends the side she's on and opens a both part; from a part under a minute old (the toast's "Back and forth" right after a Switch, or a feed just started) that part turns both instead (`resided`, and `last_tap.from` lets undo give it its side back); when that part began right as back and forth ended (Track sides, then Back and forth again within a minute), it joins that stretch, and `last_tap.cut` keeps where it began, so undo, or a side tapped within 15 s, splits it off again instead of giving the whole stretch that side. A side within 15 s of going both takes it back (`reverted`, or re-sides the both part); later, a side means "she's on the Left": tracking sides again (undo goes back to both). Pause, back on (resume on `"B"`), Done, Fix times and `setSide` ("That was both sides") work as for any part. Back and forth is its own bucket everywhere (`both` in `sideTotals`, `partTotals`, `FeedMinutes`, `both_sec` on a finished or by-minutes feed, "L 12 · R 9 · both 38"), counts toward nursing, and is never split into made-up Left and Right minutes; `first_side` / `last_side` skip it, so the start tap still decides the next side. A running both part isn't stale (`staleFeed`) for 2 hours, since it gets no taps by design. At 60 parts, going both turns the open part both instead of adding one. A paused feed at 60 parts can't go back on, Back and forth included (`too_many` with `paused`: "Tap Done and start her again"; MCP: stop_timer, then start_timer), since back on within 10 minutes still counts as the same feed.
  - **Feeds as counted** (worked out from the log, never stored: `nursingRuns`, `feedClusters`): off the breast under 10 minutes is the same feed whether Pause or Done was tapped (`SAME_FEED_MS`), so a feed paused 10+ minutes is two feeds and two feeds 5 minutes apart are one; three or more feeds, each starting less than 30 minutes after the last one ended, are a cluster (`CLUSTER_GAP_MS`). Bottles stay feeds of their own and never join a cluster. Each feed in a cluster counts toward the day's feeds ("11 · 4 in a cluster", the day line "11 feeds (one cluster)"), the same however it was tapped. `statsFor` takes the runs worked out from every loaded entry, so a feed that ran past midnight counts once, on the day it began, and its nursing minutes count with it (a day never reads 0 feeds with nursing minutes).
  - **Last fed** (`lastFedAnchor`, used by Today, the feed-gap checks and `maple_status`): from when her last feed began, start to start. A feed that went back and forth, or had 3+ parts, and ran past 40 minutes counts from 40 minutes before it ended (UNICEF UK's "between 5 and 40 minutes", `FEED_LENGTH_MIN` in `guidelines.ts`; using it this way is our choice). A feed left on one side keeps its real start, so a forgotten timer still shows its gap. So does a long feed whose last Left or Right alone ran past 40 minutes untouched (L, R, then L left on until morning), which counts from when she went on that side (`rule: "side"`). Back and forth gets no taps by design, so a long both part keeps the 40-minute rule. A later bottle wins.
  - **Next side** (`nextSideFor`): within 30 minutes of her last feed ending, the other side from the one she was last on (what the paused dock offers); after that, or while she nurses, the opposite of the side that feed started on (AAP's alternate rule, cited in `suggestNextSide`). A both-sides stretch never sets it; after back and forth it reads "Left, or the fuller side" (`fuller`, `NEXT_SIDE_NOTE`). The Done toast, and the feed sheet's toast for a feed logged by minutes, name the same side the card and the dock then show: "Left if she wants more" inside the 30 minutes, "Right next time" otherwise (`doneText` / `nextSideWords` in `useTimerActions.tsx`). "Usually every ~X" (`typicalFeedGapMin`) skips gaps inside a cluster.
  - **Timer API for it:** `start { kind: "feed", side, back_and_forth: true }` (side = where she started); `switch { id, side: "B" }` (back and forth from now); `switch { id, side: "L" | "R" }` while going both (tracking sides again); `resume { id, side: "B" }`; `reopen` / `join` and the Fix times edits take `"B"` too. Undo is `retime undo_tap` as for any tap (a start's is `discard` with `expect_updated_at`), with the same 409 `changed` races.
  - **Where it shows:** Last fed reads "Last fed 45m ago · Cluster 6:02–8:40 PM · 3 feeds · nursed 1h 52m" after a cluster ("Cluster" opens the Cluster feeding sheet), and otherwise its sides "Right first, then back and forth"; the dial stripes back and forth in both side colors (a crosshatch at night) and draws a thin bracket outside the feed ring for each cluster (a tap shows its line and feeds); the Timeline folds a day's cluster into one row that opens to its feeds. The row sits where its newest feed would be (as `list_entries` places its `feed_cluster` row), with that feed's time in the time column and the span in the line under it ("Cluster · 3 feeds   7:20 PM" / "6:50–7:40 PM · nursed 45m (L 20 · R 25)"), so a span across noon or midnight never cuts the count. It counts the cluster's own finished feeds as worked out from the whole log, so a feed's half from before a long pause isn't counted in it, and a side tapped under 10 minutes after its last Done (the same run, still running under Happening now) adds nothing to it. A past day's dial loads the day before too, so a feed that began late the night before counts on that night, as History's day line counts it. The dial opens selected entries in a detail card below the clock, with an explicit Edit action for members. Browse logged entries offers the same details through named keyboard-accessible buttons; viewers can read the details without editing. Patterns' Left/Right split leaves out back and forth and says "not counting back and forth", and finds clusters with the same rule. The one sheet about it, `sheets/ClusterInfoSheet.tsx` (`useClusterInfo()`), shows guidelines.ts's cluster block word for word (clustering is normal, back and forth is fine and switch on her cues, the sore-nipple caution, diapers and weight show she's getting enough, who to ask, 911 signs) and how the log counts. The pediatrician line points at her targets on Today only while warnings are on; otherwise `clusterCall` states her day's diaper numbers itself ("on Day 5, at least 5 wet and 3 dirty a day"). No alert is about clustering.
- **The nursing screen:** the timer card only shows what happened, as labelled rows ("Left 4:00–4:10 · 10 min", "Break · 15 min", "Right side · since 4:25"), with the time on the current side as the big number and "Total nursing · break not counted" beside it. The dock is the only place with timer actions (Switch / Pause / Done / More, one meaning per column). The night Lantern holds the same actions in the same order (Switch, Pause, Done; paused: Next side, Resume, Done). Timer toasts wait while any sheet is open, and other toasts draw inside the sheet above its footer, so nothing covers a sheet's buttons.
  - A completed side's "Finished Left/Right" row in Fix times and the saved-feed editor moves only that side's end (`side_end`). Moving it before the next side started creates a break automatically; the next side keeps its start. A switch-time correction still moves the shared boundary from the next side's start editor or the switch toast.
  - "Total nursing" is whole clock minutes, the rows' rule (each side row's minutes plus the live side's), so it never jumps at a Switch or Pause and equals the Done toast; the big number is the current side's own m:ss.
  - Forgot to stop: once a side is past its "Still nursing?" check, the dock's Done says "when?" and opens "When did she finish?" ("Now" first) instead of ending it now; the Lantern asks the same. Snoozes ("Still going") are kept per part (a side or a break), so muting one never mutes the next.
  - **Back and forth on the dock, card and Lantern** (`useTimerActions.backAndForth`, `askSide`, `trackSides`). It's offered only where it's relevant: the switch toast from a feed's second Switch ([Back and forth] over the time it records, which it sends, so a toast held while the Lantern was open still records that time, then one "2 min earlier"); the start toast of a feed that starts within 30 minutes of the last nursing feed ending ([Back and forth] after "Same feed as 6:02" within 10 minutes); and always the card's … menu ("Back and forth · Stop tracking sides from now"; on a break, "Back on, back and forth"). Its toast reads "Both sides from 6:14 · no need to tap Switch", and Undo gives the side back. While she's going both, Switch's place in the dock is a quiet "Back & forth" tile (an LR mark, "Track sides" under it) that only asks "Which side is she on now?" in a toast, [Left] [Right], and saves nothing until one is picked, so a habit tap there is harmless; Pause and Done stay put, and the menu's "Track sides · Left / Right" does the same. Picking a side is "On the Left from 9:31 · tracking sides" (within 15 s of going both it takes that back), and its Undo goes back to both. A toast raised by a chip tap (this answer, a start's [Back and forth]) ignores taps on its own chips for its first 600 ms (`ToastBody` in `ui.tsx`), so a late second tap on [Left] never lands on "2 min earlier". On a break after it, column 1 is "Track sides" (the same question; it goes back on that side, or starts a new feed after an hour) and column 2, where Pause was, is "Back on · both sides", filled, so a late second Pause tap rejoins with no break; Done is "Done · ends 8:10". The card names the part "Both sides" ("Both" in the rows, with the LR mark; on a phone under 720px tall two or more past parts fold into the one "Earlier" row, so Left, Right, then back and forth still leaves the Since tiles above the dock), and on a phone 720px or taller a line under the clock says there's no need to tap Switch, with "About back and forth" (the Cluster feeding sheet; on a short screen it's in the … menu).   - A paused feed nobody came back to for over an hour is stale (Siri's rule, judged by its newest tap that wasn't taken back): the dock's and the Lantern's side buttons say "New feed", ending it at its pause and starting a new one in one toast (Undo brings the old one back paused), and the card's "Still on a break?" leads with "She's done" ("Same feed, back on…" second).

A Continue's resume is marked `carried`, so Fix times doesn't offer an undo_tap that would leave it paused (its toast's Undo restores the Done).

## Sync diagnostics

`diagnostics-client.ts` sends bounded, best-effort batches to the authenticated, same-origin `/api/maple/diagnostics` endpoint. Vercel runtime logs with the `maple_sync` prefix record write success/failure, refresh after a write, discarded stale responses, refresh failures and recovery. `api.ts` records API responses for correlated timer and entry writes and their following state reads. Ordinary successful background polls produce no diagnostic event.

An operation gets a random, short-lived `x-maple-request-id`, reused by its following refresh so browser and server events can be matched. Fields are limited to event name, that random ID, HTTP status (0 for network failure or timeout), and elapsed milliseconds. No entry contents, entry IDs, family IDs, names, email addresses, URL queries or persistent device identifiers are included. Correlated failed API responses also reach the existing error tracker with a fixed error name, status and operation ID.

The client keeps at most eight events per batch in memory, allows 30 events per minute, and abandons a diagnostic request after four seconds without retrying or storing it. The server accepts at most 2 KiB and eight events per request and 120 submissions per member per hour, using a keyed hash for its rate-limit bucket. Diagnostics never gate a feed save.

Run `pnpm check:maple-sync` for browser regressions using intercepted synthetic responses (`pnpm exec playwright install chromium` first), `pnpm check:maple-feed-status` for the feed wording, and `pnpm check:maple-diagnostics` for logging, authentication, privacy and rate limits. The browser check's baseline override is documented in `scripts/maple-sync-check/README.md`.

## Navigation and saved history

**The rules it's built on.**
- **Her data lives only in `maple_care_*`.** No Maple path reads it: not the Timeline, Patterns, Moments, the dial, celebrations, While you slept, Recently removed, the CSV export, `AlertStack`, or Maple's MCP `list_entries`, `daily_summary`'s paragraph and per-day rows, `update_entry` and `delete_entry` (`undo_last` takes back her newest entry when it's newer than Maple's, and `log_medicine` notes when her mom has a medicine by that name, or the same medicine by its other name; `daily_summary` ends with a separate line, and `mom` in its JSON, for her own doses, temperatures and OB questions, only for someone who can read her page). Nothing about her goes in `maple_babies.settings`.
- **One rule for who sees it** (`careAccess()` in `src/lib/maple/care.ts`): everyone who can sign in to Maple's Log (owners, members, the family's admin login and the calendar connector) sees and does everything on her page; view-only guests don't. There's no per-person sharing and no "Only me". Roles are read fresh on each request, so a demoted or removed member loses it at once.
- **It works like Maple's log: no setup.** Her page always exists: `getCarePerson()` makes the one `maple_care_people` row (`DEFAULT_CARE_PERSON`, "Brittany", a plain name, so she needs no sign-in of her own) on the first read, the way the migration makes Maple's row. Deleting the page clears everything and an empty one takes its place.
- **No dose numbers anywhere by default.** Every number on a plan (how often, the 24-hour limit, how many each time, course length) is typed by the family from her label, discharge papers or clinician; fields start blank and no placeholder or hint has a digit (`npm run check:maple-care` fails on one). The app only does arithmetic on her numbers: "OK after", "OK since", "by your schedule", never "take", "due" or "time for".
- **Limits are in the label's own unit** (tablets, caplets, capsules, doses or mL), and the 24-hour count adds up each dose's units, not the taps.
- **Doses save like Maple's entries.** "Took it", Siri and the MCP save at once; early, at the limit or with the count left out still saves, and the toast or result carries the note (`earlyDose`, `overDailyMax`; a call-now note's whole text). Early means inside the gap (of the dose before, or of a later one for a back-filled dose) by more than the grace her settings give ("Early doses": Off, 15 min, 30 min or 1 hour, 30 by default; `settings.early_grace_min`, `EARLY_GRACE_*` in `guidelines.ts` with its ISMP/CMS source). `earlyGraceMin` in `care.ts` is never more than an eighth of the plan's gap and is 0 for an opioid (`EARLY_GRACE_EXACT_NAMES` = `ALL_OPIOID_NAMES`: `OPIOID_NAMES`, codeine and tramadol as `LABEL_NOT_WHILE_NURSING_NAMES` catches them, "Tylenol #3" included, and `MORE_OPIOID_NAMES`). Every one of those names also gets the opioid card (`OPIOID_NOTE`), and `ACETAMINOPHEN_NAMES` spots the acetaminophen combinations among them (Roxicet, Tylox, Lorcet, Hycet, Xodol and the like, plus Fioricet), so the plan sheet's "Contains acetaminophen" starts ticked and two acetaminophen medicines get their note. The grace doesn't add up: each dose is timed from the one before, so doses in a row within a day (`EARLY_GRACE_RUN_MS`) may come no more than the grace early in all (`graceCovers`), and three doses each 29 minutes early get the note on the third, limit or no limit. `doseNotes`, `doseFlags` and the plan card's `planNotes` all use it, so the app, Siri and Claude agree. Nothing else moves: the OK time, the duplicate check and the 24-hour limit (always checked) stay exact. A count left out counts as the most of a choice, or one when the plan doesn't say (`countedAs`), and every channel says what it counted as. An "At set times" dose more than an hour early says which time it counted for (`aheadOfSlot`). The only ask is a likely duplicate: anyone's dose of the same medicine within 30 minutes (`RECENT_MS`), plus a medicine whose doses for today are all logged, in the app. A name counts toward a plan by its name or an Also called name (`matchPlan` in `care.ts`), or one of those plus only strength and form words ("Tylenol Extra Strength", "Advil Liqui-Gels", "Ibuprofen 600"; `SAME_PRODUCT_WORDS`). Any other extra word makes it another product, which never counts toward the plan: "Tylenol 3", "Tylenol PM" or "with codeine" is a one-time medicine with its own notes (the codeine label note among them), and a plain name that's only part of a longer plan name ("tylenol" when her list has Tylenol PM, "vitamin" for Vitamin D3 and Vitamin C) asks which. Took it wears a quieter look (the sunken pill of vitamin D's "Log") while it isn't OK yet (wait, at the limit, next set time, today's all logged); it still saves at once. Its accessible name names the medicine ("Took it: Brittany's Examplex (Brandex)").
- **Names: "Examplex (Brandex)".** `planTitle(plan)` in `care.ts` is the name plus the first Also called name that isn't the name again. The strip, the picker, her tab, the Dose sheet, toasts and the Lantern use it; Siri and the MCP keep `plan.name`. On a narrow line the Also called name drops out whole before the name is cut (`PlanName` in `care/parts.tsx`). The glance (`planGlance`) is UI only: Siri's and the MCP's sentences don't change.
- **Medical copy** (warning signs, crisis card, notes, help lines, screener text) lives only in `guidelines.ts`, word for word, with its sources. Alerts say who to call (`MOM_TIER_LABEL`, or the alert's own label such as "Call Poison Help now"); readers who aren't her see "For {Name}: " before the title.

**Tables** (`src/lib/migrate.ts`):
- `maple_care_people`: the one care person per log (a single-row unique index) and `settings` (care team numbers including her therapist, nursing yes/no, next OB visit, early doses, check-in suggestions, note acks). `shared_with` is a leftover and isn't used.
- `maple_care_meds`: her plans. `schedule` is as needed (optional gap), every N hours, N times a day, or set clock times; `max_24h` needs `limit_unit`; `units_per_dose` is her own text ("2", "1 or 2"); `private` and `reviewed_at` are leftovers (nothing reads them: a plan Claude added reads like any other). Left out, how often is As needed with no gap, never a made-up number.
- `maple_care_entries`: doses (taken or skipped, with `units` and the plan's unit at the time), temperatures, questions, food and drinks. Food data is `{ description, meal: "meal" | "snack", items? }`; optional items keep a food name, portion, nutrient values, food groups, estimate/label/manual source and assumption note. Unknown nutrients stay absent or null, while zero is a recorded zero. Drink data is `{ name, amount_ml? }`, with absent or null volume meaning unknown. Rows belong to the session's family and care person, with the caregiver recorded separately. Soft deletes with Undo. The migration expands the kind constraint to accept `food` and `drink`, preserves `bp`, and can run repeatedly on existing data.
- `maple_care_mood`: check-ins and fuller check-ins, hard-deleted, its own sequence.
- Plan and entry ids are random 8-digit numbers (`care-store.ts`). The MCP prints them as `p12345678` (plans) and `c12345678` (entries).

Errors on care routes, `care-mcp.ts` and the Siri mom actions are reported as `new Error(code)` with `{ route }` only, since Postgres messages can hold row data.

**Food and drinks** (`care/NutritionSection.tsx`, `NutritionEntrySheet.tsx`, `useNutrition.tsx`):

## Notifications

Web Push, turned on phone by phone (on iPhone only from the Home Screen app, iOS 16.4+). Each phone's choices live with its subscription on the server (`maple_push_subs.prefs`), so the server knows what to send where. Code: `src/lib/maple/push.ts` (sending, ticks, health), `push-wake.ts` (when, and the QStash clock), `notify.ts` ("Logged" and the nursing timer), `push-hooks.ts` (the write hooks), `device.ts` (the per-install id), `/maple/sw.js` (the service worker), and the app's side in `src/components/maple/notify/` (the provider, the sheet and its row).

**What can be sent** (examples use a made-up medicine, Examplex):

| Notice | Who gets it | When | Default |
|---|---|---|---|
| Her medicine is OK again | Every phone of a family member with her medicines on (viewers never) | Once per phone when an as-needed or every-few-hours medicine's gap and 24-hour limit have both cleared after a dose | On |
| Set time | Same | At each set time no dose or skip has filled (the app's own slots, so a dose an hour early counts for its time) | On |
| Logged | Phones that got that medicine's reminder since its previous dose (up to 12 hours), plus phones with "every dose" on; never the phone that logged it | Seconds after a dose or skip is saved from the app, Siri or Claude | On |
| Every dose logged elsewhere | Phones that turn it on (`prefs.logged`) | Any dose of hers, even with no reminder pending | Off |
| Nursing timer on the lock screen | Every phone that turns it on (`prefs.nursing`), the one that started the feed included | Start, switch, break, back on, done, removed (and a fix while it runs) | Off |
| Test reminder | The phone that asked | One minute after "Send a test in 1 minute", through the scheduled path | On demand |

Nothing else notifies: no "timer left running", no morning summary, no readings, no feed-gap nags, and never anything about check-ins, the crisis sheet, OB questions or notes. "N times a day" medicines and as-needed ones with no gap or limit can't remind (there's no time to remind at); `GET /api/maple/push` says so per medicine (`reminders`), so the sheet never shows a switch that can't fire.

**The words.** Never a dose, never "take it now", "due" or "time for": the times are her own plan's. No person is ever named (phones aren't people); where a dose came from reads "On another phone.", "From Siri." or "From Claude.". Her own phone (signed in as herself) reads "your"; every other phone reads "for Brittany".
- OK again: "Examplex is OK again for Brittany" / "OK since 2:10 AM, by her schedule. Last taken 8:10 PM." More than 10 minutes late (the clock was down): "Examplex has been OK for Brittany since 2:10 AM" / "By her schedule. Last taken 8:10 PM.". More than 3 hours late it isn't sent at all.
- Set time: "Examplex · 8:00 AM for Brittany" / "One of Brittany's set times. Tap to log it once she's taken it."
- Logged: "Examplex logged for Brittany · 2:10 AM" / "On another phone. OK after 8:10 AM, by her schedule." (or "Next set time 8:00 PM."); a skip: "Examplex: 8:00 AM set time skipped".
- Hide medicine names: "Maple's Log" / "One of Brittany's medicines is OK again, by her schedule." (and the same for set times and Logged).
- Nursing: "Nursing · Left" / "Since 2:05 AM. Tap to open."; "Nursing · Right" / "Since 2:17 AM · feed started 2:05 AM"; "Nursing · on a break" / "Since 2:30 AM"; "Fed 23 min · L 14 · R 9" / "Done at 2:28 AM"; "Feed removed". Silent (no sound), no emoji; a tap opens `/maple`.

**On the lock screen.** Every notice about a medicine has the tag `med:<planId>` and every feed `nurse:<entryId>`. iOS ignores tag replacement, so the worker closes the notices the new one replaces before showing it (`getNotifications()`): the same tag, any other feed's nursing notice, and medicine notices older than 12 hours. So "Logged" replaces "OK again" instead of stacking, and the nursing notice is always the one feed as it is now (two quick taps that cross keep the newer one). A tap on a medicine notice opens `/maple?care=1&plan=<id>`, Logged opens `/maple?care=1`. The worker asks an open app to go there itself (`postMessage({ type: "maple-open", url })` with a MessageChannel; the app answers `{ ok: true }`), so a half-filled sheet survives; with no answer in 600 ms it navigates the window. Each push also carries a `Topic`, so a phone that was offline gets only the newest notice per tag, and a TTL of what's left of the 3-hour window (nursing: 15 minutes).

**Sent once, even when sending fails.** Nothing is queued: each tick works out what's due from the plans and doses as they are now (`dueMoments` in `push-wake.ts` is the only place that decides when), so a dose logged, moved or deleted never leaves a stale reminder. Every send is claimed per phone in `maple_push_sent` (`s<subId>|ok:<plan>:<dose>`, `…|at:<plan>:<slot>`, `…|log:<dose>`, `…|nurse:<entry>:<version>`). A send the push service refuses for now (429, 5xx, a timeout) gives its claim back: it's tried again after 50 seconds, up to 3 attempts, and with QStash a retry wake is published for a minute later. 404/410, or a 403 about keys, marks the phone `needs_resubscribe` (the sheet shows Stopped) and it gets nothing until it turns notifications on again; its row and settings stay, so turning it back on (`{ replaces }`) keeps hidden names and muted medicines. A phone left stopped for 30 days is deleted. "Logged" and the nursing notice aren't worked out from the plans, so the tick re-sends one that failed (`retryWriteNotices`, within the hour, still up to 3 attempts), and a failed one asks for its own retry wake. The retry wake is timed from the end of the run, so every claim it made is past its 50 seconds. One phone's or one member's trouble never stops the rest of the run.

**The clock.**
- **Upstash QStash (the real clock).** Every write of hers (a dose, a skip, an edit, a delete or restore, a plan saved, stopped or deleted, a move out of Maple's log) from any channel runs `careChanged()` after the response (`after()`): "Logged", a tick, and then `scheduleWakeups`, which publishes a delayed QStash message (`Upstash-Not-Before`) for each of the next 3 moments within 7 days (and any pending test) to `/api/maple/push/tick`. Turning a phone on (or moving it, or changing its settings) runs `scheduleWakeups` too, so the family's first phone gets the reminders its dose toast promised. A moment already published is a `wake:<second>` row, so it's never published twice; nothing is ever cancelled (a stale wake just finds nothing to send). On time to within about 10–20 seconds. A QStash schedule, `maple-tick-net`, runs the tick every `MAPLE_TICK_NET_MIN` minutes (default 30, at :04 and :34 like the GitHub backstop, so they wake Neon together; 0 turns it off) while any phone has notifications on, and is switched off when none does. QStash's requests are signed (`Upstash-Signature`, checked with `QSTASH_CURRENT_SIGNING_KEY` / `QSTASH_NEXT_SIGNING_KEY`); a signed call skips the 20-second gate.
- **The GitHub workflow** (`.github/workflows/maple-reminders.yml`, every 5 minutes, `X-Maple-Via: gh`) is a best-effort backstop: GitHub runs scheduled jobs late or not at all under load. Once QStash is set up, the tick route answers runs away from :04 and :34 (the safety net's minutes) with a 204 before touching the database, so Neon can sleep.
- **An open app's polls** run a tick after answering (throttled), but never publish anything. While QStash is set up, a poll leaves a pending test to the clock, so the test says whether the clock works.
- **A cron with `Authorization: Bearer $CRON_SECRET`** (for example a daily Vercel cron to `/api/maple/push/tick`) counts as trusted (`via=daily`) and re-arms everything.
- **Without any QStash env vars** nothing is published: the GitHub workflow (every 5 minutes, when GitHub runs it), open apps and writes drive the tick. Health says `mode: "fallback"`.
- The tick answers 204 with no body to everyone (a count would tell an outsider when her medicines come up), and 500 to a trusted caller when it fails, so QStash retries.
- Neon: QStash wakes touch the database only around real moments, plus the safety net (every 30 minutes is about half the compute of every 15). A one-minute pinger would keep Neon awake all day; don't use one.

**"The other phone".** The app sends a per-install id with every request (`X-Maple-Device`, `localStorage["maple-device"]`, from `deviceId()` in `src/lib/maple/device.ts`). It's stored on the phone's subscription (`device_id`; a phone that was on before ids existed gets its id from its next check, `GET /api/maple/push`, and the migration gave every phone a receipt token), on her doses and on Maple's timers (`device` columns that nothing in Maple's views reads), and used only so "Logged" skips the phone that did it. It's never shown, never names anyone and never decides access. Siri and assistant writes have none.

**Receipts and health.** Each payload carries the phone's receipt token and the notice's key; the worker posts them to `POST /api/maple/push/receipt` right after showing it (no session: the 128-bit token is the proof; always 204), which sets `last_delivered_at` and resets `undelivered`. `GET /api/maple/push?endpoint=` returns `health`: the clock (`mode`, `net_min`, `checked_at` for any tick, `clock_at` for the server's own, `clock: "on_time" | "late"`, `next_wake_at`), this phone's `last_sent_at`, `last_delivered_at`, `undelivered` (2 or more: they aren't arriving), `needs_resubscribe`, its latest `test` (`due_at`, `sent_at`, `via`, `arrived_at`), long `gaps` in the server's checks and `missed` reminders in the last 12 hours, and this member's `phones` (labels only, never endpoints). A missing receipt isn't proof a notice failed (iOS can show a notice without running the worker), so "didn't reach" waits for two in a row.

**Send a test in 1 minute.** `POST /api/maple/push/test { endpoint, in_seconds: 60 }` sets `test_due_at`, and a QStash wake sends "Test reminder" / "This phone gets reminders, even when it's locked." through exactly the path a 3am reminder takes (wake → tick → push service → worker → receipt), so it can be checked with the phone locked. `test_via` says which tick sent it (`poll` means only because an app was open). With `all: true` an owner sets one for every phone on that login (the shared admin login's phones included). Without `in_seconds` it sends "Notifications are on" at once.

**On the phone.** `NotificationsProvider` (`src/components/maple/notify/`, mounted once in `MapleApp`) holds this phone's state and renders the one Notifications sheet, portaled to `<body>` so it opens on top of whatever asked for it. `useNotifications()` gives `status` (`on`, `off`, `stopped`, `denied`, `install` for an iPhone Safari tab, `app` inside the iOS or Android app (no notifications there yet; see [`mobile.md`](mobile.md)), `unsupported`), `prefs`, `health`, `value` (the row's "On", "Off", "Stopped", "Home Screen app first", "Not in the app yet", or "On · may be late" while the server's clock is behind) and `open()`, `turnOn()`, `turnOff()`, `setPrefs()`, `testInOneMinute()`, `sendNow()`, `refresh()`, `forgetThisPhone()`; `NotificationsRow` is the "Notifications" row in Settings → This phone and on her tab.
- **The sheet**, top to bottom: what's in the way (Home Screen steps in a Safari tab, "off in Settings", or "Stopped" with a Turn on button); the switch; her medicines for anyone who can see them (Reminders, When one is OK again, At set times, Logged on another phone, Every dose logged elsewhere, Hide medicine names, then each medicine with what it can do: "When it's OK again", "At 8:00 AM and 8:00 PM", or a row with no switch, "No reminder: this one has no set times." / "No reminder: no gap set."); Maple's "Nursing timer on the lock screen" (off by default); "Check it works": the server's clock and this phone's last delivery ("Checked 2 min ago. Last one reached this phone at 3:10 AM.", "Last checked at 1:40 AM, so notifications may be late. For a dose that matters overnight, set an alarm too.", two undelivered in a row, a reminder a gap made impossible), **Send a test in 1 minute** (it re-reads every 5 seconds until the test arrives, says when it came only because the app was open, and asks "Did it show up?" when the worker sent no receipt), "Send one now", and for owners "Test every phone"; the Silent and Focus footnote; and "Phone settings that help" (iPhone and Android settings paths, Apple Watch mirroring, Show Previews).
- **Asked when it matters.** After a dose is saved on a phone whose notifications are off (supported, not denied) and that medicine has a next time by her schedule, the dose toast gets a "Remind me / at 12:56 PM" chip beside **Edit time**. One tap turns this phone on (the permission prompt is asked inside the tap, before anything waits) and says "Notifications are on for this phone. It'll say when Examplex is OK again, at 12:56 PM.". In an iPhone Safari tab it reads "Get reminders on this phone" and opens the Home Screen steps. At most 3 times per phone (`localStorage["maple-remind-offers"]`), never once on, never beside a call-now note.
- **Checked on each open** (on load and on coming back, at most once an hour), for members and viewers alike: the browser's subscription is compared with what the server has and what this phone remembers (`localStorage["maple-push-endpoint"]`: the endpoint it turned on, and for whom). An endpoint the browser swapped is saved again quietly with the old one's settings; a subscription that's gone, was made with an old key, is `needs_resubscribe`, or that the server dropped reads **Stopped**, with a toast "Notifications stopped on this phone. Turn them back on?" (Turn on / Not now; at most once a day, three days after Not now). Turn on always makes a fresh subscription and keeps the phone's settings.
- **Saved choices and failed turn-off:** a refresh cannot replace a newer notification preference while it saves or after it completes. Turning off succeeds when either the server removes the subscription or the browser unsubscribes. If both fail, the sheet retains its known state and shows retry guidance.
- **Stale notices** are closed while the app is open: a medicine's "OK again" or set time once a dose (or skip) of it was logged after it went out, a feed's notice once the app shows that feed finished, and any medicine or nursing notice older than 12 hours.
- **A tapped notice with the app open**: the provider answers the worker's `maple-open` by putting the sheet away and handing the URL to the app as a `maple-open` window event (CareNav routes it); `/maple` alone is answered at once.
- **Signing out** turns this phone's notifications off first (`forgetThisPhone()`: DELETE, then unsubscribe); if the session ends some other way while the app is open, the browser's subscription is dropped too, so the server forgets it at its next send.

**Routes.** `GET/POST/PATCH/DELETE /api/maple/push` (this phone's key, health and reminder facts; a viewer's health has no `next_wake_at` or `missed`, which are her medicines' times; subscribe with `X-Maple-Device`, or `{ replaces }` from the worker's `pushsubscriptionchange`; prefs; turn off), `POST /api/maple/push/test`, `POST /api/maple/push/receipt`, `GET/POST /api/maple/push/tick`. Prefs (each phone's, replaced whole by PATCH): `meds` (her medicines at all, default on), `ok` (OK again, default on), `at` (set times, default on), `closing` (Logged after a reminder this phone got, default on), `logged` (every dose, default off), `hide_names`, `muted` (plan ids), `nursing` (default off).

**Keys.** VAPID keys come from `VAPID_PUBLIC_KEY` / `VAPID_PRIVATE_KEY` when set, else they're derived from `MCP_SECRET` (or `GOOGLE_CLIENT_SECRET`). Changing that secret changes the keys and every phone has to turn notifications on again, so pin them first (step 5 below).

## Site metrics

The designated operator can open `/maple/admin`, or Settings → Administration → Site metrics after signing in with their own account. The shared Admin password and other family owners do not grant access. `src/lib/maple/admin/auth.ts` pins a SHA-256 digest of the authorized canonical member identity, keeping the address out of this public repository. Every metrics request checks the existing signed session and current family membership before the separate operator check; the page itself is only an empty client shell until that request succeeds.

Metrics also requires a 12-hour HttpOnly proof issued only after Google, email or Apple directly verifies the operator's original email, before linked-identity resolution. The proof uses the independent current Maple session key, never its previous key. Family switching and native-ticket exchange cannot issue it, so legacy shared credentials cannot be promoted to global metrics access. An existing login can use the page's Google or email verification to obtain it. Signing out clears it. The normal family session remains unchanged.

`GET /api/maple/admin/metrics` returns aggregate counts only, with `Cache-Control: no-store`. Family totals, signup trends, accepted account totals and recent activity exclude the original family (id 1). Accounts are deduplicated across families; pending invitations, the Admin pseudo-account and anonymous invite-link identities are excluded from the account count. Setup complete means family status `active`; recent activity instead uses members' `last_seen_at` from app state requests. The 7/30-day cards use rolling windows, while the daily signup chart covers today and the preceding 29 UTC dates. Counts describe records still present, not an immutable historical ledger.

Clickable metrics open paginated family, account or waitlist lists through `GET /api/maple/admin/details`. Lists contain generic family IDs, dates, setup status and masked contacts, with no names, entry contents or chat content. Full emails are not hidden in the initial response: an explicit Reveal action calls `POST /api/maple/admin/reveal` with an encrypted, purpose-bound reference that expires after 15 minutes. That endpoint rereads the current record. All admin endpoints require the same live membership and 12-hour operator proof; POST actions require same-origin JSON. Responses are uncached. Revealed addresses stay only in the current page's memory and can be hidden again.

Waitlist rows offer **Preview invitation**, then **Send invitation** for that one recipient. The preview uses the same fixed subject and message as the send. Its short-lived token binds the waitlist record, address and message version; sending rechecks eligibility, open sign-up and Resend configuration. Existing accounts and already-notified recipients are blocked. `maple_waitlist_outreach` is an additive, global operator table with one claim per waitlist entry and campaign. The atomic claim and stable Resend idempotency key prevent concurrent clicks or retries from issuing another email. Provider acceptance is recorded as sent, not proof of delivery. An interrupted or ambiguous send stays pending or unknown and must be checked in Resend before any manual recovery. Removing a waitlist record removes its outreach records too. Previewing, revealing, deployments and background jobs never send a launch invitation.

Checks: `pnpm check:maple-tenancy admin admin-details admin-email`. The tests use synthetic database records and email transports; never point them at production or send a real waitlist email as a test.

PostHog measures public visits, signup conversion, onboarding and allowed usage events through opaque person ids and separate family groups. Use `signup_completed` for new families; `signed_up` is retired. Production reporting filters `schema_version = 2`, `environment = production`, and `is_test = false`. Earlier events cannot reconstruct a visit-to-signup funnel because their identities were separate. See [analytics](analytics.md) for event definitions, privacy boundaries and health checks. The database dashboard works independently of PostHog configuration and delivery.

## Usage alerts

`vercel.json` schedules `GET /api/maple/usage-alerts` daily at 12:04 UTC. It requires `Authorization: Bearer $CRON_SECRET`, compared in constant time. Resend sends usage notices only to `MAPLE_ALERT_EMAIL`, defaulting to `hello@maplebaby.app`; its normal key and domain configuration are required. Notices contain counts, amounts and internal family ids, never chat content or member addresses. Check with `pnpm check:usage-alerts` and `pnpm check:maple-tenancy usage-alerts`.

- Thresholds are 50%, 80% and 100% of other families' shared monthly chat budget (default $25 per UTC month), family 1's monthly chat budget (default $5 in its timezone), other families' combined upload tokens (120 per UTC day and 2,700 lifetime), saved photos (1,500 per family except family 1), and sign-ups (default 25 in a rolling 24 hours). Budget and signup overrides match their enforcement settings. Full images and thumbnails each consume an upload token; saved-photo counts include soft-deleted moments. Upload claims serialize across families so concurrent requests share the same daily and lifetime limits; family 1 is exempt.
- Daily upload checks cover yesterday and today in UTC. Signup checks find the highest rolling-24-hour count at signup timestamps on each of those days, so yesterday's peak is still checked. Chat checks cover both the current and previous month, using UTC for the shared budget and family 1's timezone for its budget. `maple_usage_alerts` deduplicates each metric, period and threshold: UTC date for daily metrics, the relevant month for chat, and lifetime for total uploads and saved photos. Failed sends remain pending for retry with the same content and idempotency key. A separate lifetime notice is queued on the first AI Gateway `insufficient_funds` refusal from either chat path.
- The first successful check each month compares the previous complete UTC month's stored micro-dollar estimates with charged spend for the `maple-chat` Gateway tag, then emails both totals and their difference. Parsing and arithmetic use integer micro-dollars. [Gateway custom reporting](https://vercel.com/docs/ai-gateway/observability-and-spend/custom-reporting) requires Pro or Enterprise, costs $0.005 per query, and uses the project's OIDC token or `AI_GATEWAY_API_KEY`. Report access failures send a notice and retry on the next daily check. The shared tag can include synthetic evaluation requests, and configured estimates can differ from charged spend; review differences before treating them as accounting errors.
- An authenticated `GET /api/maple/usage-alerts?health=1` returns 204 only when a successful check was recorded within 36 hours; otherwise it returns 503. A successful check requires all pending deliveries and the monthly comparison to complete. Health accepts either `CRON_SECRET` or `MAPLE_USAGE_MONITOR_SECRET`; the monitor key cannot run the usage check.
- `.github/workflows/maple-usage-health.yml` independently checks health at 12:45 UTC daily and supports a manual run. Set the same `MAPLE_USAGE_MONITOR_SECRET` in Vercel and GitHub Actions, plus GitHub's `MAPLE_USAGE_MONITOR_RESEND_KEY` (a separate domain-scoped sending key) and optional `MAPLE_ALERT_EMAIL`. Its script defaults to `hello@maplebaby.app`, emails on a failed health check, and leaves the job failed even if the email succeeds. Before launch, configure these secrets and observe an authenticated usage execution, its saved completion record, its expected operator email and the independent workflow execution.

## Email

Transactional email goes out through Resend (installed from the Vercel Marketplace on the `maple` project), from `Maple <hello@${RESEND_EMAIL_DOMAIN}>` with replies to `hello@maplebaby.app` (`REPLY_TO`, held equal to `CONTACT_EMAIL` by the check). Email sign-in sends a requested one-time code. Addressed invites send after their row is created, and a new family's owner gets a welcome email after sign-up creates the family. Code: `src/lib/email/` (`send.ts`, `templates.ts`, `limit.ts`, `notices.ts`) and `src/lib/maple/email-auth.ts`; `pnpm check:email`. Sign-in configuration is in [auth.md](auth.md).

- **Env:** `RESEND_API_KEY` and `RESEND_EMAIL_DOMAIN` (`maplebaby.app`), in the intended deployment environments. Without either, `sendEmail` answers `{ sent: false, reason: "off" }` instead of throwing; invites offer a link to copy and email sign-in stays hidden. Email sign-in also needs a session signing key (`MAPLE_SESSION_SECRET`, with the legacy `GOOGLE_CLIENT_SECRET` fallback).
- **Sign-in codes:** six digits, valid for ten minutes and one successful use, bound to an HttpOnly browser cookie. The database holds an HMAC of the code and encrypted email/flow context, not a plaintext code. Five guesses exhaust a challenge. Sends wait at least 60 seconds for the same address, with caps of five per address per hour, 20 per connection per hour and `MAPLE_EMAIL_AUTH_DAILY_MAX` across everyone per day (default 1,000; zero pauses sends). Counts use keyed hashes. Expired challenges are cleared on later requests. A failed send cannot authenticate anyone. Register `hello@maplebaby.app` with Apple's private email relay before relying on delivery to Hide My Email addresses.
- **`sendEmail`** takes `to`, `subject`, `text`, `html`, a `kind` for error reports and an optional `idempotencyKey` (Resend sends a repeated key once within 24 hours; build it from ids such as `invite/<id>`, never from an address). It never throws: a bad address or subject is `invalid` before Resend is asked, and a Resend error or a failed request is `failed`, reported through `captureServerException` as the error's kind and status only (`validation_error 422`). No address, subject or body reaches a log or a report. The SDK prints Resend's error bodies to the console outside production, so `resendTransport` turns that off.
- **Templates** (`templates.ts`) take every name as an argument and escape it: `inviteEmail({ inviter, baby, link, expiresAt, timeZone })` (the expiry is written in the family's zone, "until Tuesday, November 3 at 4:05 PM EST") and `welcomeEmail({ name, baby })`. Names lose line breaks and bidi controls and are cut at 40 characters; only an http(s) link is accepted. Copy follows the site's voice: no em dashes, no exclamation marks, no "we".
- **The cap** (`limit.ts`): `allowInviteEmail(sender)` allows `INVITE_EMAILS_PER_DAY` (20) invite emails per sender in any 24 hours and counts the one it allows. The count lives in `upload_rate_limit` under an HMAC of `invite-email:<sender>` (hourly windows summed over the last day, cleared after a day like the other limits), so no address is stored. It fails closed: no database or an error means no email, and the invite falls back to its link.
- **The domain:** `maplebaby.app` is verified in Resend (us-east-1) with DKIM at `resend._domainkey` and the bounce path on `send` (MX and SPF), all in Vercel DNS. The root MX and SPF belong to Forward Email, which forwards `hello@` to Matt; leave them alone. `_dmarc` is `v=DMARC1; p=none`, with no `rua`, so no reports arrive. Open and click tracking are off on the domain (`PATCH /domains/{id}` with `open_tracking` and `click_tracking` false, read back with `GET`); Maple does not measure email opens or clicks.
- **Testing a send:** only to Resend's test address `delivered@resend.dev`, with made-up names, then `GET /emails/{id}` until `last_event` is `delivered`.
- **Delivery:** `emailInvite` checks `allowInviteEmail` before sending with `invite/<id>` as the idempotency key. A missing configuration, cap, error or slow response leaves the copy-link flow available. `emailWelcome` uses `welcome/<familyId>` and runs after a new family is created, never on a repeated sign-in or accepted invite. Its greeting uses the owner's first name, with no baby name before onboarding.
- **Retention and legal copy:** invite links expire after seven days, but used and expired rows keep their email address. Revoking an unused invite or replacing it with a new invite to the same address deletes that row; a family deletion removes its invites. `/privacy` describes this retention, Resend's recipient and message data, its sending records, limited PostHog events and feedback by email. `/terms` asks owners to invite only people who expect it. Changes to these behaviors need matching legal copy and a new `LEGAL_VERSION` / `LEGAL_UPDATED`.
